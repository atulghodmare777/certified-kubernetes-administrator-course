# Init Containers ,sidecar container , colocated container
- Take me to [Init-Containers](https://kodekloud.com/topic/init-containers/)

In a multi-container pod, each container is expected to run a process that stays alive as long as the POD’s lifecycle. For example in the multi-container pod that we talked about earlier that has a web application and logging agent, both the containers are expected to stay alive at all times. The process running in the log agent container is expected to stay alive as long as the web application is running. If any of them fails, the POD restarts.

 

But at times you may want to run a process that runs to completion in a container. For example a process that pulls a code or binary from a repository that will be used by the main web application. That is a task that will be run only one time when the pod is first created. Or a process that waits for an external service or database to be up before the actual application starts. That’s where initContainers comes in.

 

An initContainer is configured in a pod like all other containers, except that it is specified inside a initContainers section, like this:

 

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
  labels:
    app: myapp
spec:
  containers:
  - name: myapp-container
    image: busybox:1.28
    command: ['sh', '-c', 'echo The app is running! && sleep 3600']
  initContainers:
  - name: init-myservice
    image: busybox
    command: ['sh', '-c', 'git clone <some-repository-that-will-be-used-by-application> ;']
```
When a POD is first created the initContainer is run, and the process in the initContainer must run to a completion before the real container hosting the application starts.

You can configure multiple such initContainers as well, like how we did for multi-containers pod. In that case, each init container is run one at a time in sequential order.

If any of the initContainers fail to complete, Kubernetes restarts the Pod repeatedly until the Init Container succeeds.

```yaml 
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
  labels:
    app: myapp
spec:
  containers:
  - name: myapp-container
    image: busybox:1.28
    command: ['sh', '-c', 'echo The app is running! && sleep 3600']
  initContainers:
  - name: init-myservice
    image: busybox:1.28
    command: ['sh', '-c', 'until nslookup myservice; do echo waiting for myservice; sleep 2; done;']
  - name: init-mydb
    image: busybox:1.28
    command: ['sh', '-c', 'until nslookup mydb; do echo waiting for mydb; sleep 2; done;']
```

# 📦 Kubernetes Sidecar & Co-located Containers

## 📌 Overview

In Kubernetes, a Pod can contain multiple containers. Based on how they behave and interact, they are categorized as:

- Init Containers
- Sidecar Containers
- Co-located Containers (Multi-container Pods)

---

# 🚀 Sidecar Containers

## 📌 What is a Sidecar Container?

A Sidecar Container is a helper container that runs alongside the main application container in the same Pod and enhances or supports its functionality.

- Runs continuously with the main container
- Shares network and storage (volumes)
- Starts with the Pod and stops when the Pod stops

---

## 📌 Common Use Cases

- Logging agent (e.g., Fluentd)
- Monitoring agent
- Config reloader
- Proxy (e.g., Envoy)
- Service mesh sidecars (Istio)

---

## 📌 Key Characteristics

- Runs in parallel with the main container
- Does NOT block application startup (unlike init containers)
- Communicates via:
  - localhost
  - Shared volumes

---

## 📌 Example: Logging Sidecar

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: sidecar-example
spec:
  containers:
  - name: app-container
    image: busybox
    command: ['sh', '-c', 'while true; do echo "Hello from app" >> /var/log/app.log; sleep 5; done']
    volumeMounts:
    - name: log-volume
      mountPath: /var/log

  - name: log-sidecar
    image: busybox
    command: ['sh', '-c', 'tail -f /var/log/app.log']
    volumeMounts:
    - name: log-volume
      mountPath: /var/log

  volumes:
  - name: log-volume
    emptyDir: {}
📌 Explanation

app-container writes logs to /var/log/app.log

log-sidecar reads and streams logs

Both share the same volume (emptyDir)

📦 Co-located Containers (Multi-container Pods)
📌 What are Co-located Containers?

Co-located Containers are multiple containers inside the same Pod that:

Work together as a single unit

Share network (same IP)

Share storage (volumes)

Note: Sidecar is a type of co-located container pattern.

📌 Patterns of Co-located Containers

Sidecar Pattern → Supporting container

Ambassador Pattern → Proxy for external communication

Adapter Pattern → Data transformation

📌 Example: Ambassador Pattern
apiVersion: v1
kind: Pod
metadata:
  name: ambassador-example
spec:
  containers:
  - name: app-container
    image: busybox
    command: ['sh', '-c', 'sleep 3600']

  - name: ambassador-proxy
    image: busybox
    command: ['sh', '-c', 'nc -lk -p 8080 -e echo "Proxy running"']
📌 Explanation

app-container → Main application

ambassador-proxy → Acts as a proxy

Both containers run together in same Pod

🔥 Difference: Init vs Sidecar vs Co-located Containers
Feature	Init Container	Sidecar Container	Co-located Containers
Execution	Runs before app starts	Runs with app	Runs together
Lifecycle	One-time (to completion)	Continuous	Continuous
Startup Blocking	Yes	No	No
Restart Behavior	Retries until success	Restarts with Pod	Restarts with Pod
Purpose	Setup / Initialization	Support main container	General collaboration
Example	DB wait, config setup	Logging, proxy	App + proxy
